# Driver conformance

One command tests every Driver through its command line, using that Driver's `dev stand-in` instead of the vendor tool. It imports no Driver code and uses temporary homes, loopback vendor listeners and synthetic Keychain values in isolated test services. It needs no vendor account, external network or quota. Thirty-eight scenarios cover Subscription operations, fresh runs, request defaults, event ordering, complete blocks, usage totals, concurrent runs and slow readers, large tool results, conversation continuity and native history rebuilding, active run records, cancellation, shell-group cleanup, recovery after killing a Driver, control refusals, questions and their answers, unexpected permission requests, owner skills and MCP servers, background completion, and startup or partial-output failures. C26–C30 also cover error mapping, vendor wait hints, early credential rejection, start/idle/total limits, paused idle clocks and cached run-derived usage. C5 checks refusal and forced cancellation of an actual Driver run, including shell cleanup. C7 checks credential redaction in events, errors, state and text output. C32 checks every command and option, file/stdin requests, exit codes, development probes, a one-message build check and live-account refusals. Development commands use the scenario's stand-in and isolated test Subscription, never a real vendor.

Use Node.js 24 (`nvm use`), run `npm ci` and `npm run build`, and build the Driver being checked. Then:

```sh
npm exec -- arbol-conformance --driver ../arbol-claude-driver/bin/arbol-claude-driver.mjs
npm exec -- arbol-conformance --driver arbol-claude-driver --only C31,C32
```

The second form uses an installed launcher on the search path. A command with fixed arguments is one quoted value, for example `--driver 'node ../arbol-claude-driver/bin/arbol-claude-driver.mjs'`. Quote paths with spaces inside that value too. Words are split without running a shell; substitutions, pipes and redirects are never evaluated. Executables and existing relative file arguments resolve from the caller's working folder. `--only 'C31 C32'` also works; unknown or unimplemented identifiers fail before any Driver starts.

For the Codex subscription implementation, build both repositories, then run `node test/conformance-subscriptions.mjs ../arbol` from `arbol-codex-driver`. It runs C1, C2, C6, C39 and C41 and the exported subscription portions of C4, C5, C7, C8 and C40. The report names each partial scope. The normal shared scenarios retain their inference checks, including C5's active-run refusal and cancellation. C2 discovers the vendor-login family and handles either a caller-entered code or a device code shown with an `open_url` step. C7 and C8 discover families as well; C41 tests the offered families' usage and catalog behavior. Codex's stand-in records each app-server request in addition to process launches, so pagination, account renewal and absence of inference requests can be checked without a vendor account.

For Codex history and continuity, run `node test/conformance-continuity.mjs ../arbol` from `arbol-codex-driver`. It runs the full shared C14 scenario, including saved conversation checks, all rebuild reasons, native tool/image history, visible text fallback, competing resumes and map invalidation after failure. C14 checks Codex app-server injection and ephemeral threads through recorded RPCs and Codex rollouts under `sessions`; it checks Claude through its native session files and CLI arguments. Both Drivers use the same caller history and assertions.

Each scenario gets a new private home, both contract settings filenames naming `<home>/tool/vendor-tool`, a shell launcher calling the selected Driver's `dev stand-in`, and `<home>/tool/scenario`. Driver invocations work in that home with a minimal environment and `ARBOL_TEST_TIME_SCALE=100`; authentication scenarios use 10 where replacement must allow real subprocess startup, then 100 for the expiry check. C29 uses 10 for every part except the one that tests the start limit, so that starting the stand-in on a busy machine cannot reach that limit. `received.jsonl` is parsed and checked alongside stdout and exit status. Subprocesses have a 15 second deadline and 4 MiB output limit; their process groups are ended before the home is removed, including on failure or cancellation. Keychain items created by a scenario are removed in its cleanup.

The report names each scenario and its scope. A failed assertion prints its expected and received values. Exit status is 0 when every selected scenario passes, 1 when any scenario fails, and 2 for invalid input or an interrupted suite. `npm test` checks the runner's own failure reporting, isolation, selection and process cleanup using a synthetic Driver with a different version protocol.

To add a scenario:

1. Add a module under `scenarios/` exporting a `Scenario` with `id`, `title`, `scope`, `covers` and `run(home)`; register it in `scenarios/index.ts`.
2. Use `home.part('part')`, `home.call(...)` / `home.json(...)`, `home.start(...)` for streaming sign-in, `home.settings(...)`, `home.received()` and the helpers in `check.ts`. Judge only the contract and recorded tool activity. Keep vendor protocol knowledge in each Driver's stand-in, whose scripts cite raw probe evidence.
3. Add the corresponding scenario parts to each Driver's stand-in, run the scenario, and name the check in the specification's requirement table. State partial coverage in `scope`; do not claim the remaining checks pass.
