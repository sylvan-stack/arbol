# Numbered Builds

`arbol-builds` implements BLD-0 in `~/Artifacts/arbol/builds/00-builds-and-versions.md`. It belongs to this repository and is installed independently of the application or any numbered Build. It is typed Python that uses only the standard library (BLD-D15). Its code is in `src/arbol_builds/`, its checks in `tests/test_builds.py`.

Install it from `~/repos/sylvan-stack/readonly/arbol`, the clone that always holds the last merged `main` (BLD-D18):

```sh
uv sync --locked --group dev
uv run --no-sync python scripts/install_builds.py
```

The install command puts the tool into `~/.local/bin/.arbol-builds/`, together with the global Root catalogue tool `arbol-roots` and the same pinned standalone CPython 3.14.8 that every Build carries (`scripts/python-distribution.json`; the archive is taken from `~/.cache/arbol-driver-build/python` and checked by its SHA-256, or downloaded once). It compiles that Python's standard library and the tool, and writes the program `~/.local/bin/arbol-builds`, which starts the tool with that Python. `--bin-dir /absolute/path` installs into another folder; the path must not contain a space or a `#` and must be short, because both global tools and every launcher name their Python in their first line. Such a folder is refused before anything changes. Installing again stages and compiles both `arbol_builds` and `arbol_roots`, replaces each package with rollback if its staging cannot commit, writes both global entry points, and rewrites every launcher already in that folder with the current launcher code, keeping the component and the registry each one serves, launchers written by the earlier Node.js tool included (BLD-D14). Other files there are left as they are. One install runs at a time, and it removes what a stopped install left behind: unpacking and staging folders, and temporary program and launcher files whose writer has ended. A step it is stopped in is undone, including the processes it started. Run the first install, which replaces Node.js launchers, while no component is starting: a Node.js launcher that starts at the moment it is rewritten can fail once with a Node.js error. `bin/arbol-builds` starts the tool from this checkout, with the checkout's development Python; launchers it writes name that Python until the next install rewrites them.

```sh
arbol-builds build arbol-claude-driver
arbol-builds build arbol-root --root sapling
arbol-builds build arbol-trunk/trivial
arbol-builds list
arbol-builds show arbol-claude-driver
arbol-builds show arbol-claude-driver@a
arbol-builds withdraw arbol-claude-driver@a --reason 'Fails with the updated vendor tool'
arbol-builds lock arbol-claude-driver@a
arbol-builds unlock arbol-claude-driver@a
arbol-builds prune arbol-claude-driver --keep 4
```

The default repository is `~/repos/sylvan-stack/readonly/<component>`, and for a Trunk, the component `arbol-trunk/<code name>`, its folder `~/repos/sylvan-stack/readonly/arbol-trunk/trunks/<code name>/`: the clones that always hold the last merged `main` and that nobody edits, never the repositories' own folders, which can hold unmerged edits or another branch (BLD-D18). `build --repo <folder>` selects another checkout. `--registry-dir <folder>` selects another registry; the default is `~/Library/Application Support/Arbol/builds/`. `--bin-dir <folder>` selects where component launchers go; the default is `~/.local/bin`. Options work before or after the command, as `--name value` or `--name=value`.

A Build of `arbol` or `arbol-root` is made for one Root: `build --root <identifier>` names it, and the tool writes it as `root` into the record when the build starts, so the build commands and the checks find it there. The build is refused without `--root` for those two and with it for every other component, before a number is reserved. A Root identifier is one lower-case word of letters and digits; the tool does not check that the Root exists. A Trunk's code name is one lower-case word of 1 to 32 letters and digits that starts with a letter and is not `run`, `settle` or `list`. Each Trunk counts its Builds by itself in `builds/arbol-trunk/<code name>/`, and every command takes its name, as in `show arbol-trunk/trivial@4`. A Trunk gets no launcher of its own: the build of any Trunk writes the launcher `arbol-trunk`, which every Trunk shares (RCT-0, below). `list` and `show` choose Root-component defaults as described below; Trunk compatibility selection remains in `arbol-trunk`.

Each repository describes its own build:

```json
{
  "component": "sample",
  "build": ["cp program.sh \"$ARBOL_BUILD_DIR/program.sh\""],
  "entry": "program.sh",
  "checks": [{"name": "sample-check", "command": "\"$ARBOL_BUILD_DIR/program.sh\" --check"}]
}
```

Build and check commands run with `/bin/sh -c` in the repository, in a session of their own, with every signal at its default and none blocked, standard input from `/dev/null`, and the open-files limit raised as far as the system allows, as the Node.js tool gave them. They receive the caller's environment with `ARBOL_BUILD_DIR` and `ARBOL_BUILD_NUMBER` added; when `LC_ALL` is not set and the caller's character type comes out as `C` (`LC_CTYPE=C`, `LANG=C` or no locale variable), it holds `LC_CTYPE=C.UTF-8` instead, which Python sets. The build commands place a complete runnable program in that folder, including an executable `entry`. Check commands start this program directly, while its record still says `building`. They must check the output they intend to validate. A Driver also declares positive `contract` and `dataFormat` numbers and checks of all three kinds: `unit`, `contract` and `live`. A Trunk declares `rootContracts`, the versions of the Root Contract it implements, such as `[1]`: at least one positive whole number, each once, and no `contract`. No other component declares `rootContracts`. The tool copies it into the record. Its live check must send the one real test-account message BLD-0 requires. A nonzero check stops the build, names the failed check, and leaves `build.json` and `build.log` with status `failed`. The package version is read from the repository's `package.json`.

Build numbers are lower-case hexadecimal counts per component. An atomic directory creation reserves a number; failed builds, damaged records and pruned folders still consume theirs. Records are replaced atomically, in the same form as the earlier Node.js tool wrote them. Times are in the form `toISOString` writes; a record with a time outside the ECMAScript date-time format counts as damaged, where the Node.js tool also accepted other forms that `Date.parse` understands. Short process reservations in each component's `.writers/` folder serialize record changes, withdrawal and pruning; dead writers are ignored. The reservation files are those of the earlier tool, so the two tools exclude each other while both exist. Compilation and checks run outside these reservations, and launching or listing does not use them. A build interrupted by SIGINT or SIGTERM sends SIGTERM to the running command's process group, SIGKILL two seconds later if it is still there, and is recorded as failed. After an uncatchable kill the incomplete record stays `building` and cannot run.

Each component launcher is one standalone Python file that uses only the standard library: the text of `src/arbol_builds/launcher.py` followed by the call that serves its component and registry. Its first line names the Python of the `arbol-builds` that wrote it. It reads the records each time, chooses the highest working Build that still has its executable, sets SIGPIPE and SIGXFSZ back to their default, which Python changes when it starts, and then uses `os.execv` to replace itself with that executable. `sample -v 1 ...` selects Build 1 only when `-v` is the first argument. Arguments and environment, byte for byte, the working folder, standard streams, PID, signals and the exit status reach the Build directly. When `LC_ALL` is not set and the caller's character type comes out as `C`, the Build sees `LC_CTYPE=C.UTF-8` instead, which Python sets, and macOS adds `__CF_USER_TEXT_ENCODING` when the caller did not set it. A name given twice and an entry without `=` reach the Build as they are, where the Node.js launcher passed only the first value and dropped the second kind. A Ctrl-C while Python itself starts ends the launcher by SIGINT before the Build starts, but can print `KeyboardInterrupt` first, and rarely Python stops with status 1 instead; the first line after the interpreter line delivers again an interrupt that Python's start-up caught. A closed standard input, output or error reaches the Build as `/dev/null`, as with the Node.js launcher. Unlike that launcher, the Python launcher leaves the open-files limit as the caller set it. Withdrawn Builds, and failed Builds that still have their executable (BLD-D13), run only when named and print why on stderr. A failure field that is not the object BLD-0 describes shows as `see build.log`, or with Python's text for a missing part, where the Node.js launcher printed `undefined`. Refusals print a JSON error and the available build numbers. A hand-over the system refuses prints `launch_failed`.

The launchers `arbol` and `arbol-root` embed `launcher.py`, `roots.py` and `root_launcher.py`. They accept only the ordered selection prefix `[--root <identifier>] [-v <build>]` and pass all later arguments unchanged, including an empty command. The default is the highest runnable working Build of the named Root, or the current Root, read on every start with the same reader as `arbol-trunk`. A named Build uses its recorded Root and requires that Root’s readable record; conflicting selectors are refused. Explicit preparing or failed Roots are usable, but the implicit current Root must be working. No Build of another Root is a fallback. The launcher adds no Root argument: the Build knows its own Root from its record. Refusals use `unknown_root`, `build_unavailable` or `invalid_input`, with available Builds restricted to the selected Root (BLD-D21). Reinstallation upgrades older Root-component launchers and refreshes this new form too.

The launcher `arbol-trunk` starts every Trunk (RCT-0, BLD-D17). It is the text of `launcher.py`, `roots.py` and `trunk_launcher.py` in `src/arbol_builds/`, without their imports from the package, followed by one call that names the registry. Its call is `arbol-trunk [--root <root>] [<code name>] [-v <build>] <command> …`: `--root` counts only as the first argument, and the next argument is the code name unless it is `-v`, `run`, `settle`, `list` or begins with `-`. At every start it reads `root.json` of the Root named, or of every Root to find the current one, the working Root created last, in `~/Library/Application Support/Arbol/roots/` under the home folder, so a test gives it a home of its own. It takes the Trunk named, or `trivial`, and the newest working Build of it whose `rootContracts` hold the Root's `rootContract`, or the Build named with `-v` when it fits, and starts it as a component's launcher does, handing it `--root <root>` before the command and everything after it unchanged. `arbol-trunk list` it answers itself, from the records alone: the Root, its version, and every Trunk with its Builds, marking the one `run` would start; after a code name, that Trunk alone. It refuses with `invalid_input` (no command, or `list` after `-v` or with more after it), `unknown_root`, `unknown_trunk` and `no_fit`, in one line with `available`, the runnable Builds of the Trunk that fit the Root, beside `error`.

Before handing over, both launchers replace `last-start` in the chosen Build's folder with the current UTC millisecond timestamp and a newline. The write is best effort: it takes no lock, retries nothing, does not flush to disk, and never prevents a launch if writing fails. A failed write keeps the previous timestamp. Named failed and withdrawn Builds are recorded too; refusals and `arbol-trunk list` are not. Reinstalling with the command above refreshes both component launchers and `arbol-trunk`, so existing Builds need no rebuild to receive tracking.

`list` and `show` add `lastStart` (a UTC timestamp or null) and `unusedSince` to their output without storing either field in `build.json`. A damaged or unreadable regular timestamp file falls back to its modification time. Missing or nonregular files mean no recorded start; `unusedSince` then uses `finishedAt`, or `startedAt` for an unfinished build. An older Build with no record may already have run. Pruning preserves `last-start` alongside the record and log.

`lock component@build` marks any known, unpruned Build with `lockedAt`, including one still building or one that failed or was withdrawn. Repeating a lock preserves its original time. `unlock component@build` removes the mark, and succeeds unchanged when there is none. Both print the stored record and refuse unknown or pruned Builds. List and show include the timestamp; an invalid timestamp makes the record damaged. A running Build preserves the current mark or its absence at each record write, so finishing cannot undo a concurrent lock or unlock.

`list [component] --root <identifier>` marks the defaults for that Root in `arbol` and `arbol-root`, while a whole-registry list keeps global defaults for other components. Without a selector, it uses the current Root; with none working it still lists every record, marking no Root-component default. `show arbol-root --root sapling` returns the same Root-specific default. A named `show arbol-root@6` preserves record introspection even after that Root’s record is gone, but refuses an explicit conflicting Root selector. Explicit non-Root component inventory refuses `--root`.

`list` returns records with a `default` boolean; `show` returns one record, including retained failed or pruned records when named. `prune --keep <n>` requires a positive whole number. It removes files only from older working Builds, preserving the default, every Locked Build, withdrawn Builds, failed Builds, records and logs. Older Locked Builds are retained in addition to the newest requested working count. Locking and pruning use the same per-component reservation: lock-first keeps the files, and prune-first makes the subsequent lock fail. A retained record marks removed files with `prunedAt`. Components continue to guard the format of their own shared data; this tool records the declared format without modifying that data.

Count-based pruning also keeps the newest runnable working Build of each retained Root for `arbol` and `arbol-root`, and of each required Root Contract version for a Trunk. These protections add to the count, Locked Builds and existing default protection; one Trunk Build may cover several versions. A Root is retained while its valid identifier folder has a `root.json` entry, including preparing/failed Roots and damaged or unreadable entries. For Root components, the folder identifier still protects its Build. For Trunks, one retained Root without a readable valid record refuses the whole prune before changing anything, because its version is unknown. A missing catalogue means no retained Roots; another listing error refuses Root/Trunk pruning. Drivers and other components never read the Root catalogue and retain count/lock behavior. The pruning-only reader in `src/arbol_builds/pruning.py` reuses Root validation but never enters launcher text. It reads one snapshot under the component reservation; later catalogue changes enter the next prune’s view (BLD-D22).

The on-demand latency check is `uv run --no-sync python tests/launcher_benchmark.py --python <interpreter> [--node-launcher <file>]`. It builds a tiny sample twice, then times rounds that start the Build's program directly and through the launcher. On 15 October 2026, on this arm64 Mac, with the installed tool's pinned Python, the Python launcher added a median of 15.19 ms (95th percentile 16.96 ms) over 60 rounds; a launcher of the earlier Node.js tool (Node 24.21.0), timed in the same rounds, added 23.46 ms (26.44 ms). The Node.js launcher's own measurement of 7 October 2026 was 21.51 ms added. The same benchmark times the launcher `arbol-trunk` against a direct start of the same Trunk Build: on 16 October 2026, with the same Python and 60 rounds, it added a median of 15.49 ms (95th percentile 16.83 ms) for `run` with the current Root, and 15.57 ms (16.70 ms) for the call `arbol-root` makes, which names the Root, the Trunk and the Build, against 14.07 ms (15.10 ms) for a component's launcher in the same rounds. The records stay on this machine, in `builds/evidence/` (`launcher-benchmark-2026-10-15-installed.json`, `launcher-benchmark-2026-10-16-trunk.json` and `launcher-benchmark-2026-10-07.json`), which git leaves out like every result of a check.

The same installation writes `arbol-roots`, the global catalogue outside every Root (SYL-160). Its commands are `create <root> --name <text> [--from <root>] [--root-contract <version>]`, `list`, `show [<root>]`, `ready <root>`, `fail <root> --reason <text>`, `app <root> <build>` and `remove <root>`. It uses the shared Root header/current selection, creates only empty databases through maintenance psql, and never embeds a Root's table layout or implementation. A Root stays preparing until ready finds a runnable compatible working Trivial Trunk. Removing the current Root is refused. Before an App Build exists, the record's app minimum is the bootstrap string 0; an available minimum can later be raised, never lowered. migrate/layout remain SYL-185.

State and settings default to `~/Library/Application Support/Arbol/roots/` and `~/.arbol/roots/`; `--roots-dir`, `--settings-dir`, `--registry-dir`, `--database-config`, create's `--database-name`, and executable overrides `--psql`/`--security` isolate checks. Catalogue mutations serialize through `.catalogue.lock`; records are replaced atomically. A failed creation rolls back confirmed new work; an uncertain SQL outcome or failed rollback retains a private `.creating.json` recovery receipt rather than risking an existing database. A failed DROP leaves files intact; later filesystem cleanup reports incomplete removal for retry. No command uses DROP FORCE.

The catalogue unit checks are in `tests/test_roots.py`. `uv run --no-sync python scripts/roots_drill.py` repeats the damaged-record drill with a private home, registry and actual standalone Trunk launcher, without a database/vendor request. `uv run --no-sync python tests/test_roots.py --real-server` explicitly qualifies the lifecycle against uniquely named disposable databases on the installed server, reads the existing database credential through a delegate that names the owner's login Keychain, and cleans up all of its databases and folders. No password is written to a test file or output. Both checks accept `--tool /absolute/path/to/arbol-roots` to qualify an installed tool. The real-server checker alone opens its disposable Root databases to prove emptiness; the global tool's lifecycle operations connect only to postgres. `tests/test_builds.py` additionally exercises both installed programs, existing launcher refresh and stopped-install cleanup. The package rollback check covers compilation failure and interruption between directory renames for both packages.
